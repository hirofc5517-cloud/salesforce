# Apex 標準リファレンス

Apexは「宣言的機能（Flow・入力規則等）で実現できない場合の最終手段」です。実装前に必ず
[`docs/00-automation-decision-guide.md`](../00-automation-decision-guide.md) で他の選択肢を検討したことを確認してください。

## 1. いつApexを使うか

- 複雑な分岐・ループ・アルゴリズムを伴う処理
- 大量データに対する高度なSOQL/DML最適化が必要
- 複数のFlow/画面/バッチから再利用したい共通ロジック（Invocable Apexとして部品化）
- Flowの式では表現できない複雑な計算・正規表現処理
- 複雑な外部コールアウトの制御（リトライ、タイムアウト制御、独自例外処理）
- テストフレームワークが要求する高信頼性が必要な基幹ロジック

## 2. トリガーの設計規約

- **1オブジェクトにつきトリガーは1つ**（"One Trigger per Object"）。
- トリガー本体にロジックを書かず、**トリガーハンドラクラス**に処理を委譲する（Trigger Handler Framework）。
- すべてのDML/beforeイベントは **バルク処理前提**（1件用に書かない。`Trigger.new` は常に配列として扱う）。
- 再帰実行防止のため、静的変数（`static Boolean isExecuting`等）でガードする。
- Flow（レコードトリガーフロー）と同一オブジェクトに対して自動化を分散させすぎない。
  同一オブジェクトの自動化はできる限り一箇所（トリガー or Flow）に集約し、実行順序の見通しを保つ。

```apex
trigger AccountTrigger on Account (before insert, before update, after insert, after update) {
    new AccountTriggerHandler().run();
}
```

## 3. ガバナ制限（Governor Limits）— 必ず遵守

同期Apexの主な制限（1トランザクションあたり）:

| 項目 | 制限値 |
|---|---|
| SOQLクエリの発行回数 | 100回 |
| SOQLで取得するレコード数 | 50,000件 |
| DML発行回数 | 150回 |
| DMLで処理するレコード数 | 10,000件 |
| CPU時間 | 10,000ms（同期） / 60,000ms（非同期） |
| ヒープサイズ | 6MB（同期） / 12MB（非同期） |
| コールアウト回数 | 100回 |
| コールアウトのタイムアウト | 最大120秒（合計） |
| Future/Queueableの呼び出し | 1トランザクションあたり50回 |

**遵守のための実装規約:**

- **ループ内でのSOQL/DMLは禁止**。ループ前にコレクションへ集約し、ループ外で一括発行する。
- **Mapを使ったバルク処理**を徹底する（`Map<Id, SObject>` で関連レコードを一括取得）。
- 大量データ処理が必要な場合は **Batch Apex**（`Database.Batchable`）を使用し、
  `execute`メソッド内のスコープごとにガバナ制限がリセットされることを利用する。
- SOQL/SOSLは `WHERE`句・`LIMIT`句・選択的フィルタ（インデックス項目）を用いて絞り込む。

## 4. 非同期Apexの使い分け

| 種類 | 用途 |
|---|---|
| **Future Method (`@future`)** | 単純な非同期処理（コールアウト等）。戻り値なし、単純なパラメータのみ。 |
| **Queueable Apex** | Futureの上位互換。複雑なオブジェクトを渡せる、チェイニング可能。 |
| **Batch Apex** | 大量レコード（数万〜数百万件）の一括処理。 |
| **Scheduled Apex** | 定期実行（Cron式）。多くの場合はFlowのスケジュールトリガーで代替可能かを先に検討する。 |

## 5. セキュリティ規約

- 共有ルールを尊重する処理は `with sharing`、システムコンテキストで意図的に無視する場合のみ
  `without sharing` を明示し、その理由をコメントで残す。
- SOQL/SOSLに**ユーザー入力を直接連結しない**（インジェクション対策として `:bindVariable` を使用、
  動的SOQLは `String.escapeSingleQuotes()` を必ず適用）。
- CRUD/FLS（項目レベルセキュリティ）を尊重する必要がある処理（特にUIから呼ばれるコード）は
  `Security.stripInaccessible()` またはWITH SECURITY_ENFORCED（SOQL）を使用する。
- ハードコードされたID（レコードID、プロファイルID等）を書かない。カスタムメタデータ型/カスタム設定を使う。

## 6. テスト規約

- 本番組織へのデプロイには**全体で75%以上のコードカバレッジ**が必須（Salesforce標準要件）。
  ただし「カバレッジを満たすためのテスト」ではなく、**意味のあるアサーションを伴うテスト**を書くこと。
- テストデータは `@TestSetup` で作成し、本番データに依存しない（`SeeAllData=false` がデフォルト）。
- 正常系・異常系（例外発生）・境界値（0件、大量件数=バルク）の3パターンを最低限カバーする。
- `Test.startTest()` / `Test.stopTest()` でガバナ制限のリセットと非同期処理の同期実行を行う。

## 7. Apexを書く前のセルフチェックリスト

- [ ] Flow・入力規則・数式項目で代替できないか検討したか
- [ ] ループ内でSOQL/DMLを呼んでいないか
- [ ] `with sharing` を明示したか（意図的に外す場合は理由を明記）
- [ ] バルク（200件同時実行）でもガバナ制限内に収まるか
- [ ] テストクラスで正常系・異常系・バルクケースを網羅したか
- [ ] Invocable Methodとして部品化し、Flowから呼び出せる設計にできないか
