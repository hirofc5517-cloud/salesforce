# 入力規則・数式項目・ロールアップ集計 標準リファレンス

コードやFlowを検討する前に、まずこれらの「項目レベルの標準機能」で要件を満たせないか確認してください。

## 1. 入力規則（Validation Rule）

- 「保存を許可しない条件」を定義する機能。`ISBLANK()`, `ISPICKVAL()`, `REGEX()`,
  `TODAY()`, `ISCHANGED()`, `PRIORVALUE()` などの数式関数で条件を組む。
- **用途**: 必須チェックの高度化、項目間の整合性チェック（例: 終了日 < 開始日 は保存不可）、
  フォーマットチェック（郵便番号・電話番号のREGEX検証等）。
- エラーメッセージは該当項目に紐づけて表示し、ユーザーが修正方法を理解できる文言にする。
- 複雑になりすぎる（10行を超えるANDOR混在）場合は、複数の入力規則に分割して可読性を保つ。

## 2. 数式項目（Formula Field）

- **用途**: 既存項目からの計算値表示（税込金額、日数計算、文字列連結、条件付き表示など）。
- リアルタイム計算・保存不要・レポートで即座に使える利点がある。
- クロスオブジェクト参照は親方向（ルックアップ/マスタ商細の親）にのみ可能。子→親は
  `Parent__r.Field__c` のようにドット記法で辿る。
- 数式は入れ子が深くなりすぎると保守性が落ちるため、必要に応じて中間の数式項目に分割する。

## 3. ロールアップ集計項目（Roll-Up Summary Field）

- **前提条件**: **マスタ商細関係（Master-Detail Relationship）** の親オブジェクトにのみ作成可能。
  通常のルックアップ関係では使えない（その場合はFlowまたはApexトリガーで集計する）。
- **用途**: 子レコードの `COUNT` / `SUM` / `MIN` / `MAX` を親に自動集計。
- フィルタ条件を設定して集計対象を絞り込める。

## 4. 通常のルックアップ関係で「集計」したい場合

マスタ商細でない場合、以下の優先順位で検討する:

1. **レコードトリガーフロー（before-save非対応、after-saveで子→親集計）**: 子レコードの
   作成/更新/削除時に親の集計項目を更新するFlowを作成。
2. Apexトリガー: Flowでは性能・複雑性の面で対応困難な大量データの集計処理のみ。

## 5. その他の標準入力制御

| 機能 | 用途 |
|---|---|
| 必須項目設定（ページレイアウト/項目定義） | 単純な必須化 |
| 制御項目・依存項目（Controlling/Dependent Picklist） | 選択肢の連動制御 |
| Dynamic Forms | 項目の条件付き表示/非表示（コードなしでUIロジック） |
| 重複ルール・一致ルール | 重複レコードの警告・ブロック |

## 6. 実装前チェックリスト

- [ ] 入力規則で完結する単純な検証か確認したか
- [ ] マスタ商細関係であればロールアップ集計を優先したか
- [ ] 通常のルックアップでの集計はFlow(after-save)で対応可能か検討したか（Apex最終手段）
- [ ] 数式が複雑になりすぎていないか（分割を検討したか）
