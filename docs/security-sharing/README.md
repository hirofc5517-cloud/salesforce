# 権限・共有 標準リファレンス

権限制御は「最小権限の原則」と「Salesforceが推奨する権限セット中心の設計」に従うこと。

## 1. 権限モデルの基本方針

- **プロファイル（Profile）は最小限**にし、オブジェクト権限・項目権限の付与は
  **権限セット（Permission Set）／権限セットグループ（Permission Set Group）で加算していく**方式を採用する
  （Salesforce公式推奨のセキュリティモデル）。
- 職務・機能単位で権限セットを分割し（例: 「請求書承認権限」「レポート閲覧権限」）、
  ユーザーには複数の権限セットを組み合わせて割り当てる。
- 新しい権限要件が出た場合、**まずプロファイルを編集する前に、権限セットの新設・追加を検討する**。

## 2. 組織全体のデフォルト設定（OWD）と共有ルール

- Organization-Wide Default（OWD）はできるだけ**Private/Public Read Only**など厳しめに設定し、
  必要なアクセスは以下の仕組みで**加算**する:
  1. **ロール階層（Role Hierarchy）**
  2. **共有ルール（Sharing Rule）**（所有者ベース／条件ベース）
  3. **手動共有（Manual Share）**
  4. **Apex共有（Apex Managed Sharing）** ← 上記で対応できない動的・複雑な共有条件の場合の最終手段

## 3. 項目レベルセキュリティ（FLS）

- 権限セット／プロファイルの項目レベルセキュリティで、参照・編集可否を制御する。
- Apex/LWCから呼ぶコードは、ユーザー権限を無視しないよう `WITH SECURITY_ENFORCED` や
  `Security.stripInaccessible()` を用いてFLSを尊重する（[`docs/apex/README.md`](../apex/README.md) 参照）。

## 4. 認証・多要素認証（MFA）

- Salesforceは全ユーザーに対する**多要素認証（MFA）を必須要件**としている。
  新規ユーザー作成・ログイン設定の際はMFA必須を前提に設計する。
- API/外部連携用のユーザーは可能な限り**Named Credential + 専用のIntegrationユーザー
  （最小権限の権限セットのみ付与）**を使用し、個人ユーザーの認証情報を流用しない。

## 5. 実装前チェックリスト

- [ ] 権限追加はプロファイル編集ではなく権限セット（グループ）で対応したか
- [ ] OWDは必要最小限のアクセスレベルにし、共有ルールで加算する設計になっているか
- [ ] Apex共有は他の共有機能で代替できないことを確認した上での最終手段か
- [ ] Apex/LWCコードはFLS・CRUDを尊重しているか
